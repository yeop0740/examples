오픈 깃옵스(OpenGitOps) 프로젝트에 정의된 4대 깃옵스 핵심 원칙을 준수해야한다.

- 선언형 구성 : 모든 구성은 선언형 YAML파일로 작성되어 깃으로 관리. 클러스터 구성에 관한 단일 진실 공급원
- 구성 버저닝 : 모든 구성이 깃에 보관되고, 모든 변경 사항은 버저닝 된다. 변경과 롤백의 감사가 용이
- 불변 구성 : 모든 구성은 불변이다. 한번 변경하면 다시는 수정할 수 없다. 이로 인해 클러스터를 일관된 상태로 유지할 수 있다.
- 지속적인 상태 조정
클러스터의 상태는 깃에 정의된 상태와 지속적으로 동기화된다. 이 역시 클러스터를 일관된 상태로 유지하는 데 핵심적인 역할을 한다.

## 깃옵스가 필요한 이유

기존의 배포 워크플로

1. 애플리케이션 코드를 수정
2. 컨테이너 이미지 빌드
3. 이미지 레지스트리에 푸시
4. 새 컨테이너 이미지를 사용할 수 있도록 쿠버네티스 매니페스트 업데이트
5. 클러스터에 변경사항 적용

문제점
- 애플리케이션과 클러스터가 늘어날 수록 복잡해질 수 있다.
- 사람이 하는 작업이므로 에러가 나기 쉽고 문제의 원인을 쉽게 디버깅 할 수 없다.
- 변경 사항의 롤백 등이 쉽지 않다.
- 구성 드리프트가 일어날 수 있다.
- 보안 액세스 제어가 복잡해지는 경향이 있다.

gitops의 해결 방법
- 선언형 구성 : yaml파일로 작성해 깃으로 관리, 이는 클러스터 구성에 관한  단일 진실 공급원. 깃 히스토리를 통해 변경 사항 쉽게 감사 가능
- 버전 관리 : 깃을 이용하면 쉽게 변경 사항 추적 가능
- 지속적인 조정 : 클러스터 상태는 깃에 정의된 상태와 지속적으로 동기화된다. 깃에서 변경 사항은 쉽게 되돌릴 수 있어 롤백도 간편
- 보안 : 깃을 통해 관리하면 클러스터의 모든 벼경 사항에 대한 감사 로그로 이루어질 수 있다.

## 깃옵스 리포지터리 구조

일반적인 4대 전략

단일 리포지터리
쿠버네티스 매니페스트와 애플리케이션 코드를 단일 리포지터리에 저장
단순한  방법이라서 좋지만, 규모가 커지면 관리가 어려워짐
모든 팀의 소스 코드와 쿠버네티스 매니페스트가 리포지토리 한 곳에 저장되므로 관심사의 분리가 이루어지지 않는다.

**단일 리포지터리 (Mono-repo) 구조 예시**

애플리케이션 소스 코드와 쿠버네티스 배포 매니페스트를 하나의 깃 리포지터리에서 같이 관리하는 패턴입니다.

```text
console/
├── src/                    # 애플리케이션 소스 코드
│   ├── main.go
│   └── ...
├── deploy/                 # 쿠버네티스 매니페스트 (Argo CD, Flux 등 GitOps 도구가 바라보는 경로)
│   ├── deployment.yaml
│   └── ...
│   ├── service.yaml
│   └── kustomization.yaml
manage-server/
├── src/
│   ├── main.go
│   └── ...
└── deploy/
    ├── deployment.yaml
    ├── service.yaml
    └── kustomization.yaml
```

**특징:**
- **장점**: 개발과 배포 코드가 한 곳에 있어 관리 및 추적이 용이하고, 초기 프로젝트 구성이 간단합니다. 소규모 프로젝트나 단일 팀에서 관리하기 좋습니다.
- **단점**: 애플리케이션 개발자와 인프라/옵스 담당자의 권한 분리가 어려우며 코드가 방대해질 경우 리포지터리가 복잡해집니다.
- **주의사항**: CI 과정에서 템플릿의 이미지 버전 태그 등을 수정하여 같은 리포지터리에 커밋/푸시하게 되므로, 매니페스트 변경 커밋으로 인해 CI가 무한으로 재실행(무한 루프)되지 않도록 트리거 설정을 주의해야 합니다.

**팀별 리포지터리 (Multi-repo) 구조 예시**

팀별 애플리케이션 소스 코드를 각각의 독립된 리포지터리로 분리하고, 배포용 쿠버네티스 매니페스트를 관리하는 전용 리포지터리를 별도로 구성하는 패턴입니다.

- 깔끔하게 정리하고 관심사를 분리할 수 있다.
- 결국 애플리케이션이 많아지면 관리하기 어려워진다.

```text
[개발 리포지터리 1: Team A - Console App]
console-app/
└── src/                    # Team A 애플리케이션 소스 코드
    ├── main.go
    └── ...

[개발 리포지터리 2: Team B - Manage Server App]
manage-server-app/
└── src/                    # Team B 애플리케이션 소스 코드
    ├── main.go
    └── ...

[배포 리포지터리: GitOps 매니페스트 전용]
gitops-manifests/           # Argo CD, Flux 등 GitOps 도구가 바라보는 상태 관리 저장소
├── team-a/
│   └── console/
│       ├── deployment.yaml
│       ├── service.yaml
│       └── kustomization.yaml
└── team-b/
    └── manage-server/
        ├── deployment.yaml
        ├── service.yaml
        └── kustomization.yaml
```

**특징:**
- **장점**: 애플리케이션 코드와 배포 매니페스트가 분리되어 관심사의 분리(Separation of Concerns) 및 명확한 역할/권한(RBAC) 제어가 가능합니다. CI 파이프라인에서의 무한 루프 문제가 원천적으로 발생하지 않으며, 팀별 독립성을 보장합니다.
- **단점**: 관리해야 할 리포지터리 수가 증가합니다. 여러 프로젝트에 걸친 변경 사항을 한눈에 파악하기 다소 어려우며, 초기에 여러 시스템을 연동하는 파이프라인 구성이 비교적 복잡할 수 있습니다.

**애플리케이션별 리포지터리 구조 예시**

애플리케이션마다 리포지토리를 따로 두고 쿠버네티스 매니페스트는 동일한 리포지토리에 저장

- 깔끔하게 정리하고 관심사 분리 가능
- 팀 단위로 읽기만 가능하게 설정할 수 있음
- 한 곳에서 전체를 바라볼 수 없음

- 각 서비스(애플리케이션)가 완전히 독립적인 라이프사이클을 가질 수 있다.
- 애플리케이션 단위로 세밀하게 권한 제어(RBAC)가 가능하다.
- 마이크로서비스 개수만큼 리포지터리가 2배씩 늘어나 파편화가 발생할 수 있다.

```text
[리포지터리 1: Console App 소스 코드]
console-app/
└── src/
    ├── main.go
    └── ...


[리포지터리 2: Manage Server App 소스 코드]
manage-server-app/
└── src/
    ├── main.go
    └── ...

[리포지터리 3: 배포 매니페스트]
gitops-manifests/
├── console-app-gitops/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── manage-server-app-gitops/
    ├── deployment.yaml
    ├── service.yaml
    └── kustomization.yaml
```

**특징:**
- **장점**: 서비스별로 배포 파이프라인과 인프라 설정이 완전히 독립되어 있어, 한 애플리케이션의 배포 작업이나 장애가 다른 시스템에 영향을 주지 않습니다. 자율적인 마이크로서비스 운영이 필요한 조직에 적합합니다.
- **단점**: 관리해야 할 리포지터리가 폭발적으로 증가합니다. 인프라 전역에 공통적으로 적용해야 하는 변경 사항(예: 전역 Ingress 설정 변경, 라벨 체계 수정 등)이 있을 경우 수많은 리포지터리를 일일이 수정해야 하는 비효율이 발생하며, 전반적인 시스템 가시성을 확보하기 어렵습니다.

**환경별 브랜치 (Environment-specific branches) 구조 예시**

동일한 리포지터리에 환경별로 브랜치를 둔다.
이렇게 하면 머지만 해도 환경을 업데이트 할 수 있음
상이한 환경 간 예기치 않은 변경으로 충돌이 일어날 가능성이 있다.
브랜치가 너무 늘어나면 관리 부담 증가
kustomize나 helm처럼 템플릿을 활용하는 툴과 잘 맞지 않는다.

디렉토리가 아닌 **깃(Git) 브랜치**를 활용하여 배포 환경(Dev, Staging, Prod 등)을 분리하는 패턴입니다. GitOps 도구는 각각 동일한 리포지터리의 다른 브랜치를 바라보도록 설정됩니다.

- 브랜치 병합(Merge)이나 풀 리퀘스트(PR)를 통해 하위 환경에서 상위 환경으로 프로모션(승격) 수행 가능
- 단일 디렉토리 구조를 유지하면서 환경만 전환해서 볼 수 있음
- 브랜치 수명 주기가 길어져(Long-lived branches) 시간이 지날수록 브랜치 간 차이가 커질 수 있음

```text
[리포지터리: 배포 매니페스트 (gitops-manifests)]

# Branch: `dev` (개발 환경)
├── deployment.yaml
├── service.yaml
└── configmap.yaml

# Branch: `staging` (스테이징 환경)
├── deployment.yaml
├── service.yaml
└── configmap.yaml

# Branch: `prod` (운영 환경)
├── deployment.yaml
├── service.yaml
└── configmap.yaml
```

**특징:**
- **장점**: 기존 소프트웨어 개발의 브랜치 전략(Git-flow 등)에 익숙한 사용자에게 직관적입니다. 특정 환경에서 발생한 변경사항을 다른 환경의 브랜치로 쉽게 Cherry-pick하거나 Merge 할 수 있으며, 환경 단위의 롤백이 명확해집니다.
- **단점**: 환경마다 Kustomize 구조나 특화 설정이 다를 경우, 브랜치 간 Merge Conflict(충돌)가 잦아 유지보수 비용이 급증합니다. (최근 커뮤니티나 공식 베스트 프랙티스에서는 브랜치보다는 '환경별 디렉토리 분리' 방식을 더 권장하는 추세입니다)

환경별 브랜치(Environment-specific branches) 구조가 Kustomize나 Helm 같은 템플릿/오버레이 도구와 잘 맞지 않는 주된 이유는 **"동일한 파일에서 발생하는 잦은 충돌(Merge Conflict)"**과 "코드 재사용(DRY)의 불편함" 때문입니다.

구체적인 이유는 다음과 같습니다.

1. Merge 시 필연적인 충돌 발생 (Merge Conflict)
브랜치 방식으로 환경을 승격(예: dev 브랜치를 prod 브랜치로 병합)하려고 할 때, Kustomize의 kustomization.yaml이나 Helm의 values.yaml 파일 내용은 각 환경마다 구조적으로 다를 수밖에 없습니다.

dev 브랜치에는 replicas: 1이, prod 브랜치에는 replicas: 5가 설정되어 있다면, dev의 기능 업데이트(예: 이미지 태그 변경)를 prod로 Merge 할 때마다 이 설정들이 충돌(Conflict)을 일으키게 됩니다.
결국 단순한 이미지 버전 업데이트를 위해 매번 복잡한 충돌 해결 과정을 거치거나, Merge 대신 체리픽(Cherry-pick)만 수동으로 수행해야 하므로 실수할 확률이 높아집니다.
2. 도구의 설계 철학과 불일치 (폴더 지향적 특징)
Kustomize와 Helm은 하나의 브랜치 내에서 디렉토리나 파일을 통해 환경을 분리하도록 설계(Directory-per-environment) 되어 있습니다.

Kustomize: 공통 설정은 base/ 폴더에 두고, 환경별 차이점은 overlays/dev/, overlays/prod/ 폴더에 두어 재사용성을 높입니다.
Helm: 공통 템플릿은 templates/에 두고, 환경별 값은 values-dev.yaml, values-prod.yaml과 같이 관리합니다. 하지만 환경을 브랜치로 나누게 되면 이러한 도구의 네이티브(DRY)한 폴더 구조 전략을 100% 활용하기 어렵고, 도구의 본래 목적이 희석됩니다.
3. 공통 기반(Base) 파일 관리의 어려움
만약 모든 환경에 동일하게 적용되어야 하는 애플리케이션의 핵심 구성 요소(예: Deployment의 라벨 추가, 새로운 ServiceAccount 추가)가 있다면, 폴더 구조(오버레이)에서는 base 파일 하나만 수정하면 끝입니다. 반면 환경별 브랜치 구조에서는 dev, staging, prod 브랜치를 각각 체크아웃하여 동일한 base 수정본을 일일이 커밋해 주어야 하므로 유지보수 부담이 크게 증가합니다.

요약하자면, Kustomize나 Helm은 애초에 **"코드는 하나로 합치고, 설정값은 폴더/파일로 나눈다"**는 철학을 가지고 있습니다. 반면 브랜치 기반 구조는 **"설정 파일 자체가 브랜치별로 나뉜다"**는 방식이라 서로 충돌 구조를 피하기 어렵고, 결과적으로 GitOps 파이프라인 관리가 고통스러워지기 때문에 권장되지 않습니다. (최근에는 디렉토리별 환경 분리 패턴을 훨씬 더 선호합니다.)
