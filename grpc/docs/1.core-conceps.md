# 핵심 개념, 아키텍처 및 생명주기

## 개요

### 서비스 정의
많은 RPC 시스템과 마찬가지로 gRPC는 서비스를 정의하고, 원격으로 호출할 수 있는 메서드와 해당 매개변수 및 리턴 타입을 지정하는 개념을 기반으로 합니다.
gRPC는 기본적으로 프로토콜 버퍼(protocol buffers)를 서비스 인터페이스와 페이로드 메시지(payload message)의 구조를 설명하기 위한 인터페이스 정의 언어(IDL)로 사용됩니다.
필요에 따라 다른 대안을 사용할 수도 있습니다.

```proto
service HelloService {
    rpc SayHello (HelloRequest) returns (HelloResponse);
}

message HelloRequest {
    string greeting = 1;
}

message HelloResponse {
    string reply = 1;
}
```

gRPC를 사용하면 네 가지 유형의 서비스 메서드를 정의할 수 있습니다.

- Unary RPC는 클라이언트가 서버에 단일 요청을 보내고 일반 함수 호출처럼 단일 응답을 받는 방식입니다.
```
rpc SayHello(HelloRequest) returns (HelloResponse);
```

- Server streaming RPC 는
클라이언트가 서버에 하나의 요청(request)을 보내고,
그에 대한 응답으로 메시지들의 연속(sequence)을 읽을 수 있는 stream 을 받는 방식입니다.

클라이언트는 반환된 stream으로부터 메시지를 계속 읽다가,
더 이상 메시지가 없을 때까지 읽기를 수행합니다.

gRPC는 하나의 RPC 호출 내부에서는 메시지 순서(ordering)를 보장합니다.

```
rpc LotsOfReplies(HelloRequest) returns (stream HelloResponse);
```

- 클라이언트 스트리밍 RPC(Client streaming RPC) 는 클라이언트가 제공된 스트림(stream)을 사용하여 일련의 메시지를 작성하고 서버로 전송하는 방식입니다.

클라이언트는 메시지 작성을 모두 마친 뒤, 서버가 이 메시지들을 읽고 처리한 후 응답을 반환할 때까지 기다립니다.

마찬가지로 gRPC는 하나의 RPC 호출 내부에서는 메시지의 순서가 유지되도록 보장합니다.

```
rpc LotsOfGreetings(stream HelloRequest) returns (HelloResponse);
```

- 양방향 스트리밍 RPC(Bidirectional streaming RPC) 는
클라이언트와 서버 양쪽 모두가 읽기-쓰기 스트림(read-write stream) 을 사용하여 일련의 메시지를 서로 주고받는 방식입니다.

두 스트림은 서로 독립적으로 동작하므로, 클라이언트와 서버는 원하는 순서대로 읽기와 쓰기를 수행할 수 있습니다.
예를 들어:

서버는 클라이언트의 모든 메시지를 다 받을 때까지 기다린 뒤 응답을 보낼 수도 있고,
메시지 하나를 읽은 뒤 바로 메시지 하나를 보낼 수도 있으며,
또는 그 외의 다양한 읽기/쓰기 조합을 사용할 수도 있습니다.

각 스트림 내부에서는 메시지의 순서가 유지됩니다.
```
rpc BidiHello(stream HelloRequest) returns (stream HelloResponse);
```

You’ll learn more about the different types of RPC in the RPC life cycle section below.

### Using the API

.proto 파일에 정의된 service definition 을 시작점으로 하여,
gRPC는 protocol buffer compiler plugin 을 제공하며, 이를 통해 클라이언트 측 코드와 서버 측 코드를 생성합니다.

gRPC 사용자는 일반적으로:

클라이언트 측에서는 생성된 API를 호출하고
서버 측에서는 이에 대응하는 API를 구현합니다.

- 서버 측(server side) 에서는
서버가 service에 선언된 메서드들을 구현하고,
클라이언트 호출을 처리하기 위해 gRPC 서버를 실행합니다.

gRPC 인프라는:

들어오는 요청(request)을 디코딩하고
서비스 메서드를 실행한 뒤
서비스 응답(response)을 다시 인코딩합니다.

- 클라이언트 측(client side) 에서는
stub 이라고 불리는 로컬 객체(일부 언어에서는 client라는 용어를 더 선호함)가 있으며,
이 객체는 service와 동일한 메서드들을 구현하고 있습니다.

클라이언트는 이 로컬 객체의 메서드를 단순히 호출하면 됩니다.

그러면 해당 메서드는:

호출 파라미터를 적절한 protocol buffer message 타입으로 감싸고
요청을 서버로 전송하며
서버의 protocol buffer 응답을 반환합니다.

### Synchronous vs. asynchronous

서버로부터 응답이 도착할 때까지 대기(block) 하는 동기식 RPC 호출(Synchronous RPC calls) 은
RPC가 지향하는 프로시저 호출(procedure call) 추상화에 가장 가까운 형태입니다.

즉, 일반 함수 호출처럼:

호출 → 응답 올 때까지 기다림 → 다음 코드 실행

으로 동작합니다.

반면, 네트워크는 본질적으로 비동기적(asynchronous) 이며,
많은 상황에서는 현재 스레드를 막지 않고(blocking 없이) RPC를 시작할 수 있는 것이 유용합니다.

즉:

호출 시작 → 현재 thread 계속 작업 수행 → 나중에 응답 처리

가 필요할 수 있습니다.

대부분의 언어에서 gRPC 프로그래밍 API는:

동기식(synchronous) 방식
비동기식(asynchronous) 방식

두 가지 형태를 모두 제공합니다.

추가적인 내용은 각 언어별 tutorial 및 reference documentation에서 확인할 수 있으며,
완전한 reference 문서는 곧 제공될 예정입니다.

### RPC life cycle

이 섹션에서는 gRPC 클라이언트가 gRPC 서버의 메서드를 호출할 때 내부적으로 어떤 일이 일어나는지를 더 자세히 살펴봅니다.

구현에 대한 완전한 세부 사항은 각 언어별 문서(language-specific pages) 를 참고하면 됩니다.

### Unary RPC
먼저, 클라이언트가 하나의 요청을 보내고 하나의 응답을 받는 가장 단순한 형태의 RPC 를 살펴보겠습니다.

1. 클라이언트가 stub 메서드를 호출하면, 서버는 해당 RPC가 호출되었다는 사실을 전달받습니다.

이때 함께 전달되는 정보는 다음과 같습니다.

이번 호출에 대한 클라이언트 메타데이터(metadata)
메서드 이름(method name)
설정된 deadline(있는 경우)

즉 내부적으로는:
```
stub 호출
→ method 정보 + metadata + deadline 전달
```

2.

그 다음 서버는:

자신의 초기 메타데이터(initial metadata)를 즉시 반환할 수도 있고
(응답보다 먼저 보내야 함)

또는

클라이언트의 요청 메시지를 기다릴 수도 있습니다.

어느 것이 먼저 일어나는지는 애플리케이션 구현 방식에 따라 다릅니다.

즉:

초기 metadata 먼저 보낼 수도 있음
또는 request 먼저 받을 수도 있음

3.

서버가 클라이언트의 요청 메시지를 받으면,
응답을 생성하고 필요한 데이터를 채우기 위한 작업을 수행합니다.

응답 생성이 완료되면, 성공한 경우 다음과 함께 클라이언트로 반환됩니다.

응답(response)
상태 정보(status details)
status code
optional status message
선택적 trailing metadata

즉:

response + status + trailing metadata 반환


4.

응답 상태(status)가 OK 이면,
클라이언트는 응답을 수신하고 호출이 완료됩니다.

즉:

status OK
→ client response 수신
→ RPC 종료

### Server streaming RPC
서버 스트리밍 RPC(Server-streaming RPC) 는
기본적으로 unary RPC와 비슷하지만, 서버가 클라이언트의 요청에 대해 하나의 응답 대신 여러 개의 메시지를 스트림(stream) 형태로 반환한다는 점이 다릅니다.

서버는 모든 메시지를 전송한 뒤, 다음 정보를 클라이언트에 전달합니다.

상태 정보(status details)
상태 코드(status code)
선택적인 상태 메시지(optional status message)
선택적인 trailing metadata

이 시점에서 서버 측 처리는 완료됩니다.

클라이언트는 서버가 보낸 모든 메시지를 수신하면 호출이 완료됩니다.

### Client streaming RPC
클라이언트 스트리밍 RPC(Client-streaming RPC) 는
기본적으로 unary RPC와 유사하지만,
클라이언트가 서버에 하나의 메시지 대신 여러 개의 메시지를 스트림(stream) 형태로 전송한다는 점이 다릅니다.

서버는 하나의 응답 메시지를 반환하며, 이때 함께 다음 정보도 전달됩니다.

상태 정보(status details)
선택적인 trailing metadata

서버의 응답은 일반적으로 클라이언트의 모든 메시지를 받은 뒤 반환되지만,
반드시 그럴 필요는 없습니다.

### Bidirectional streaming RPC 
양방향 스트리밍 RPC(Bidirectional streaming RPC) 에서는
클라이언트가 메서드를 호출하면서 통신이 시작되고,
서버는 다음 정보를 전달받습니다.

- 클라이언트 메타데이터(client metadata)
- 메서드 이름(method name)
- deadline

그 다음 서버는 다음 중 하나를 선택할 수 있습니다.

- 자신의 초기 메타데이터(initial metadata)를 먼저 보낼 수도 있고
- 클라이언트가 메시지 스트리밍을 시작할 때까지 기다릴 수도 있습니다.


클라이언트 측과 서버 측의 스트림 처리 방식은 애플리케이션에 따라 달라집니다.

두 스트림은 서로 독립적 이기 때문에,
클라이언트와 서버는 메시지를 어떤 순서로든 읽고 쓰는 것이 가능합니다.

예를 들어:

서버는 클라이언트의 모든 메시지를 다 받을 때까지 기다린 뒤 자신의 메시지를 보낼 수도 있고,

또는

서버와 클라이언트가 "핑퐁(ping-pong)" 방식 으로 동작할 수도 있습니다.

즉:

서버가 요청 하나를 받고
응답 하나를 보낸 뒤
클라이언트가 그 응답을 기반으로 또 다른 요청을 보내고
이 과정이 반복되는 방식입니다.

### Deadlines/Timeouts 
gRPC는 클라이언트가 RPC가 완료될 때까지 얼마 동안 기다릴 것인지를 지정할 수 있도록 합니다.

만약 지정한 시간 안에 RPC가 완료되지 않으면,
해당 RPC는 DEADLINE_EXCEEDED 오류와 함께 종료됩니다.

gRPC는 클라이언트가 RPC가 완료될 때까지 얼마 동안 기다릴 것인지를 지정할 수 있도록 합니다.

만약 지정한 시간 안에 RPC가 완료되지 않으면,
해당 RPC는 DEADLINE_EXCEEDED 오류와 함께 종료됩니다.

즉 클라이언트는:

이 호출은 최대 3초까지만 기다린다

처럼 deadline을 설정할 수 있습니다.

예:

stub.withDeadlineAfter(3, TimeUnit.SECONDS)

서버 측에서는:

현재 특정 RPC가 이미 timeout 되었는지,
또는 얼마나 시간이 남았는지를 조회할 수 있습니다.

즉 서버는:

이미 deadline 초과 여부 확인 가능
남은 시간 확인 가능

deadline 또는 timeout을 지정하는 방법은 사용하는 언어에 따라 다릅니다.
일부 언어의 API는 timeout(지속 시간, duration) 기준으로 동작하고,
일부 언어의 API는 deadline(고정된 시점, fixed point in time) 기준으로 동작합니다.
또한 언어에 따라 기본 deadline이 존재할 수도 있고, 존재하지 않을 수도 있습니다.

### RPC termination 
gRPC에서는 클라이언트와 서버가 각각 독립적으로, 그리고 자신의 로컬 관점에서 호출의 성공 여부를 판단합니다.

따라서 양쪽의 판단 결과가 서로 일치하지 않을 수도 있습니다.

예를 들어:

서버 측에서는 RPC가 성공적으로 끝났다고 판단할 수 있습니다.

"나는 모든 응답을 전송했다!"

하지만 동시에 클라이언트 측에서는 실패로 판단할 수 있습니다.

"응답이 deadline 이후에 도착했다!"

즉:

서버는 성공 ✅
클라이언트는 실패 ❌

가 동시에 발생할 수 있습니다.

또한 서버가 클라이언트가 모든 요청을 보내기 전에 먼저 호출을 종료하기로 결정하는 것도 가능합니다.

즉:

client request 아직 남음
→ server는 먼저 종료 결정

도 가능합니다.

### Cancelling an RPC
클라이언트와 서버 어느 쪽이든 언제든지 RPC를 취소(cancel)할 수 있습니다.

취소가 발생하면 해당 RPC는 즉시 종료되며,
그 이후의 추가 작업은 더 이상 수행되지 않습니다.

> warning
Changes made before a cancellation are not rolled back.

### Metadata
Metadata 는 특정 RPC 호출에 대한 정보(예: 인증 정보)를 의미하며,
key-value 쌍의 목록(list) 형태로 표현됩니다.

여기서:

key는 문자열(string)이고
value는 일반적으로 문자열(string)이지만,
binary data일 수도 있습니다.

Metadata의 key는 대소문자를 구분하지 않으며(case insensitive),
다음 문자들로 구성됩니다. ASCII 문자(letter), 숫자(digit),특수문자, `-`, `_`, `.`

또한 key는 grpc- 로 시작해서는 안 됩니다(접두사는 gRPC 내부 용도로 예약(reserved)되어 있기 때문입니다).

그리고 value 유형에 따라 key 이름 규칙이 다릅니다.
binary value인 경우 key는 반드시 `-bin` 으로 끝나야 합니다.
ASCII value인 경우 `-bin` 을 붙이지 않습니다.

사용자가 정의한 metadata(user-defined metadata) 는 gRPC 자체에서 사용되지 않습니다.
즉, gRPC는 이를 내부적으로 해석하거나 특별한 의미를 부여하지 않습니다.
대신 이것은:
클라이언트가 호출과 관련된 정보를 서버에 전달하거나
서버가 호출과 관련된 정보를 클라이언트에 전달하는 데 사용할 수 있습니다.

Metadata에 접근하는 방법은 사용하는 언어에 따라 다릅니다.

### Channels
gRPC 채널(channel) 은
지정된 호스트(host) 와 포트(port) 의 gRPC 서버에 연결을 제공하는 객체입니다.
이 채널은 클라이언트 stub을 생성할 때 사용됩니다.

즉 구조적으로는:
Channel 생성
→ Stub 생성
→ RPC 호출

클라이언트는 channel argument 를 지정하여
gRPC의 기본 동작(default behavior)을 변경할 수 있습니다.

예를 들면:
메시지 압축(message compression) 사용 여부 설정
timeout 관련 옵션 설정
keepalive 설정

또한 channel은 상태(state) 를 가집니다.

대표적인 상태는:
connected
idle

gRPC에서 channel을 종료(close)하는 방법은 사용하는 언어에 따라 다릅니다.
또한 일부 언어에서는 channel의 상태(state)를 조회하는 기능도 제공합니다.
