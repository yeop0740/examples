# 04. Large Response Body

## 목적

응답 본문이 커질 때 전송 효율과 직렬화 비용 차이를 비교한다.

## 시나리오 개요

- 요청은 작게, 응답은 크게 유지한다.
- 조회 API처럼 서버가 큰 데이터를 반환하는 상황을 가정한다.

## 고정 조건

- request body는 `1KB` 이하
- 헤더는 최소 수준
- 서버 비즈니스 로직은 데이터 생성 또는 메모리 기반 조회로 단순화
- 압축은 기본적으로 비활성화

## 주요 변수

| 항목 | 값 |
| --- | --- |
| response 크기 | `10KB`, `100KB`, `1MB`, `5MB` |
| client 수 | `5`, `20`, `100` |
| 목표 부하 | `20`, `100`, `300 RPS` |

## 요청 정의 예시

- 상품 목록 조회, 배치 결과 조회, 통계 조회
- REST는 JSON 응답
- gRPC는 unary response 메시지

## 실행 절차

1. 동일 의미의 응답 데이터를 준비한다.
2. 응답 크기만 단계적으로 증가시킨다.
3. 각 크기 단계에서 클라이언트 수를 늘리며 측정한다.
4. 2분 warm-up, 5분 측정, 3회 반복한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- 응답 전송량
- 서버 CPU 사용률
- NIC 사용량 또는 네트워크 처리량
- 에러율

## 기대 관찰 포인트

- 응답이 커질수록 wire size와 serialization 효율 차이가 더 잘 드러난다.
- 특정 크기 이상부터는 CPU보다 네트워크 대역폭이 병목이 되는지 확인할 수 있다.

## 주의사항

- unary로 큰 응답을 보내는 경우와 streaming으로 나누는 경우를 혼동하지 않도록 한다.
- 클라이언트 측 메모리 사용량도 함께 보는 편이 좋다.
