# 15. Server Near Saturation

## 목적

서버 CPU, worker, thread pool이 포화에 가까워질 때 latency와 에러 증가 패턴을 비교한다.

## 시나리오 개요

- baseline small unary 또는 high RPS 시나리오를 기반으로 부하를 계속 올린다.
- 서버가 정상 구간에서 포화 구간으로 넘어가는 지점을 찾는다.

## 고정 조건

- 서버 자원 한도 고정
- 비즈니스 로직 단순화
- 네트워크와 헤더 조건 단순화
- 커넥션 재사용

## 주요 변수

| 항목 | 값 |
| --- | --- |
| 목표 CPU 구간 | `50%`, `70%`, `85%`, `95%+` |
| 목표 부하 | 단계적으로 증가 |
| client 수 | `5`, `50`, `200` |

## 실행 절차

1. 낮은 부하부터 시작해 1분 단위로 점진적으로 RPS를 올린다.
2. 각 구간에서 CPU, queue, error를 기록한다.
3. `p99`가 급격히 증가하는 knee point를 찾는다.
4. 프로토콜별로 knee point가 어디서 나타나는지 비교한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- CPU 사용률
- queue length 또는 backlog
- 에러율
- 실제 달성 RPS

## 기대 관찰 포인트

- 평상시 차이가 작아도 포화 구간에서는 에러율과 tail latency 차이가 크게 나타날 수 있다.
- 프로토콜 차이보다 구현체의 worker 모델 차이가 더 큰지도 함께 확인할 수 있다.

## 주의사항

- autoscaling과 rate limit은 끄거나 고정해야 한다.
- 한 번 포화된 뒤 바로 다음 실험을 하면 잔여 영향이 남을 수 있으므로 휴지 구간을 둔다.
