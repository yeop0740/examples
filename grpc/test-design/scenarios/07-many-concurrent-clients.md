# 07. Many Concurrent Clients

## 목적

동시에 접속한 client 수가 많아질 때 커넥션 관리 비용과 tail latency 변화를 비교한다.

## 시나리오 개요

- 각 client의 호출 빈도는 높지 않지만 전체 client 수가 매우 많다.
- 모바일 사용자, 브라우저 사용자, 다수 edge agent를 가정한다.

## 고정 조건

- request/response는 작게 유지
- 인증/헤더는 최소화
- 각 client는 장시간 연결을 유지
- 서버 비즈니스 로직은 단순 응답

## 주요 변수

| 항목 | 값 |
| --- | --- |
| 동시 client 수 | `100`, `1000`, `5000`, `10000` |
| client당 요청 빈도 | `0.2`, `1`, `5 RPS` |
| 연결 유지 시간 | `5분`, `15분` |

## 실행 절차

1. 동시 client 수를 단계별로 증가시킨다.
2. 각 client는 낮은 빈도로 지속 요청을 보낸다.
3. server connection count와 메모리 사용량을 함께 기록한다.
4. 각 단계는 10분 이상 유지해 장기 연결 영향을 본다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- 활성 커넥션 수
- 프로세스 메모리
- 파일 디스크립터 사용량
- 에러율

## 기대 관찰 포인트

- 커넥션 수가 많아질수록 프로토콜 스택별 관리 비용 차이가 드러난다.
- `HTTP/2` 기반 연결 관리와 `HTTP/1.1`의 여러 연결 전략 차이를 비교하기 좋다.

## 주의사항

- OS의 `ulimit`, backlog, ephemeral port 설정이 실험 결과를 왜곡하지 않도록 미리 조정한다.
- LB나 proxy가 있다면 해당 장비의 connection limit도 함께 확인해야 한다.
