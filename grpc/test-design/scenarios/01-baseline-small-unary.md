# 01. Baseline Small Unary

## 목적

가장 단순한 unary 호출에서 `REST API`와 `gRPC`의 순수 프로토콜/직렬화 오버헤드를 비교한다.

## 시나리오 개요

- 요청과 응답 모두 매우 작게 유지한다.
- 비즈니스 로직은 `echo`, `ping`, `health-check` 수준으로 단순화한다.
- 서버와 네트워크가 충분히 여유 있는 상태에서 측정한다.

## 고정 조건

- 동일한 서버 인스턴스와 동일한 CPU limit 사용
- 동일한 응답 데이터 의미 유지
- 재시도, 캐시, 압축 비활성화
- 커넥션은 재사용하되 불필요한 churn은 만들지 않음

## 주요 변수

| 항목 | 값 |
| --- | --- |
| request 크기 | `128B`, `512B`, `1KB` |
| response 크기 | `128B`, `512B`, `1KB` |
| client 수 | `1`, `5` |
| 목표 부하 | `100`, `500`, `1000`, `3000 RPS` |

## 요청 정의 예시

- REST: `POST /v1/ping`
- gRPC: `PingService/Ping`
- payload: 문자열 1개, 숫자 2개, boolean 1개 정도의 단순 구조

## 실행 절차

1. 서버를 단독 환경에서 실행한다.
2. `REST + HTTP/1.1`, 가능하면 `REST + HTTP/2`, `gRPC + HTTP/2`를 각각 준비한다.
3. 2분 warm-up 후 5분 동안 부하를 유지한다.
4. 각 부하 단계별로 3회 이상 반복 측정한다.
5. 각 반복 사이에 1분 정도 휴지 시간을 둔다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- RPS
- 서버 CPU 사용률
- 프로세스 메모리
- 네트워크 바이트
- 에러율

## 기대 관찰 포인트

- 매우 작은 메시지에서는 직렬화 비용보다 프로토콜 처리 비용 차이가 크게 보일 수 있다.
- `HTTP/1.1 REST` 대비 `gRPC`는 connection reuse와 binary serialization 이점이 나타날 가능성이 있다.
- `REST + HTTP/2`를 함께 보면 프로토콜 차이와 데이터 포맷 차이를 분리해서 해석하기 쉽다.

## 주의사항

- 서버 로직이 조금만 무거워져도 프로토콜 차이가 묻힐 수 있다.
- 로깅, tracing, DB 호출은 제외하는 것이 좋다.
