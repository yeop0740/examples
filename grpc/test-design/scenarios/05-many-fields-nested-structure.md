# 05. Many Fields / Nested Structure

## 목적

필드 수가 많고 구조가 깊은 메시지에서 `REST API`와 `gRPC`의 구조 해석 비용 차이를 비교한다.

## 시나리오 개요

- 전체 바이트 수만이 아니라 필드 수, 중첩 깊이, 반복 필드 수를 변화시킨다.
- 실제로는 주문, 장바구니, 사용자 프로필, 권한 목록 같은 복합 응답을 가정한다.

## 고정 조건

- 전체 payload 크기는 케이스 간 큰 차이가 나지 않게 맞춘다.
- client 수와 부하는 중간 수준으로 고정한다.
- 헤더와 네트워크 조건은 단순하게 유지한다.

## 주요 변수

| 항목 | 값 |
| --- | --- |
| 구조 유형 | 평면 `20 fields`, 평면 `100 fields`, depth `3`, depth `5` |
| repeated field 개수 | `0`, `10`, `100` |
| 총 payload 크기 | `10KB`, `50KB` |
| 목표 부하 | `100`, `300`, `1000 RPS` |

## 요청/응답 정의 예시

- 사용자 + 주소 + 권한 + 조직 + 설정 + 태그 목록
- 주문 + 주문항목 + 할인 + 배송 + 결제 + 메타데이터

## 실행 절차

1. 총 데이터 의미는 유지하되 구조 복잡도만 바꾼다.
2. 각 구조 유형에 대해 같은 부하를 걸어 비교한다.
3. 2분 warm-up 후 5분 측정한다.
4. 구조가 복잡할수록 CPU profile도 함께 기록한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- CPU 사용률
- 메모리 할당량 또는 GC 횟수
- wire size

## 기대 관찰 포인트

- 단순 크기보다 구조 복잡도가 더 큰 영향을 주는 구간이 있는지 확인할 수 있다.
- JSON 파싱은 필드 수와 nested object 수 증가에 더 민감할 가능성이 있다.

## 주의사항

- 총 payload 크기가 다르면 구조 복잡도와 크기 효과가 섞이므로 가능한 비슷하게 맞춘다.
- 누락 필드, optional field 처리 규칙도 동일하게 유지한다.
