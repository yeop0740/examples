# 13. Compression On / Off

## 목적

메시지 압축이 네트워크 사용량과 CPU 비용에 어떤 trade-off를 만드는지 비교한다.

## 시나리오 개요

- 압축 가능성이 높은 payload와 낮은 payload를 모두 사용한다.
- 작은 payload보다 중간 이상 payload에서 효과를 본다.

## 고정 조건

- 커넥션 재사용
- 서버 로직 단순화
- TLS 여부는 별도 고정

## 주요 변수

| 항목 | 값 |
| --- | --- |
| payload 크기 | `10KB`, `100KB`, `1MB` |
| payload 유형 | text-heavy, random-like |
| 압축 모드 | off, `gzip` |
| 목표 부하 | `50`, `200`, `500 RPS` |

## 실행 절차

1. 압축이 잘 되는 텍스트 중심 payload를 준비한다.
2. 압축 효과가 낮은 랜덤 데이터 payload도 준비한다.
3. 각 payload에 대해 압축 off와 on을 비교한다.
4. REST와 gRPC에서 동일한 압축 수준으로 맞춰 측정한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- CPU 사용률
- 네트워크 바이트 절감률
- 실제 처리량
- 에러율

## 기대 관찰 포인트

- 네트워크가 병목인 구간에서는 압축이 유리할 수 있다.
- CPU가 병목인 구간에서는 압축이 오히려 불리할 수 있다.
- payload 특성에 따라 압축 효과가 크게 달라지는지 확인할 수 있다.

## 주의사항

- 압축 알고리즘과 레벨이 다르면 결과가 크게 변하므로 반드시 고정한다.
- 작은 payload에서는 압축 자체가 왜곡 요소가 될 수 있다.
