# 10. High Latency Network

## 목적

RTT가 큰 네트워크 환경에서 `REST API`와 `gRPC`의 응답 지연과 처리량 차이를 비교한다.

## 시나리오 개요

- 서버 로직은 단순하게 유지하고 네트워크 지연만 인위적으로 증가시킨다.
- 리전 간 통신, 원거리 클라이언트, 하이브리드 네트워크를 가정한다.

## 고정 조건

- 작은 unary 호출 사용
- packet loss는 최소화
- 헤더 최소화
- 커넥션 재사용 활성화

## 주요 변수

| 항목 | 값 |
| --- | --- |
| RTT | `10ms`, `50ms`, `100ms`, `200ms` |
| client 수 | `5`, `50` |
| 목표 부하 | `100`, `500`, `1000 RPS` |

## 실행 절차

1. `tc netem` 같은 도구로 RTT를 단계적으로 부여한다.
2. 각 RTT 조건에서 동일한 payload와 부하를 사용한다.
3. `REST + HTTP/1.1`, `REST + HTTP/2`, `gRPC + HTTP/2`를 비교한다.
4. 각 조건에서 5분 이상 측정한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- 실제 달성 RPS
- 재전송 여부
- 커넥션 수
- 에러율

## 기대 관찰 포인트

- RTT가 커질수록 연결 재사용과 multiplexing 전략의 차이가 더 잘 드러난다.
- `HTTP/2` 기반 통신이 높은 지연 환경에서 상대적으로 유리한지 확인할 수 있다.

## 주의사항

- RTT 외에 packet loss와 jitter가 섞이지 않도록 별도 통제한다.
- 서버와 클라이언트 모두 동일한 네트워크 정책 아래 있어야 한다.
