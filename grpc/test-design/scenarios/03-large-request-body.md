# 03. Large Request Body

## 목적

요청 본문이 커질 때 `JSON` 기반 `REST API`와 `protobuf` 기반 `gRPC`의 직렬화/역직렬화 비용 차이를 확인한다.

## 시나리오 개요

- 요청은 크게, 응답은 작게 유지한다.
- 서버는 요청을 파싱한 뒤 간단한 검증 결과만 반환한다.

## 고정 조건

- response body는 `1KB` 이하
- 헤더는 최소 수준으로 유지
- 커넥션 재사용
- 압축 비활성화

## 주요 변수

| 항목 | 값 |
| --- | --- |
| request 크기 | `10KB`, `100KB`, `1MB`, `5MB` |
| payload 형태 | 평면 배열, 중간 중첩 구조 |
| client 수 | `5`, `20` |
| 목표 부하 | `20`, `100`, `300 RPS` |

## 요청 정의 예시

- 상품 목록, 이벤트 배치, 로그 배치 업로드처럼 큰 입력을 받는 unary 호출
- REST는 JSON 배열/객체
- gRPC는 repeated field 또는 bytes field 기반 메시지

## 실행 절차

1. 논리적으로 동일한 payload를 REST와 gRPC에 각각 정의한다.
2. request 크기만 단계적으로 증가시키고 응답은 고정한다.
3. 각 단계에서 2분 warm-up, 5분 측정한다.
4. CPU가 과도하게 포화되면 다음 단계 전 결과를 별도 기록한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- 서버 CPU 사용률
- GC 또는 메모리 사용량 변화
- 네트워크 바이트
- 에러율

## 기대 관찰 포인트

- request parsing 비용이 커질수록 `protobuf`의 이점이 더 분명해질 수 있다.
- 큰 JSON body에서는 CPU와 메모리 할당 비용이 tail latency에 직접 반영될 가능성이 높다.

## 주의사항

- 실제 서비스가 text 중심 데이터인지 binary 중심 데이터인지에 따라 결과 해석이 달라진다.
- `5MB` 이상은 프레임 크기 제한과 메시지 최대 크기를 먼저 점검해야 한다.
