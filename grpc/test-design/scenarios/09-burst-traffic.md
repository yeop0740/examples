# 09. Burst Traffic

## 목적

짧은 시간에 트래픽이 급증할 때 큐 적체와 tail latency 증가 패턴을 비교한다.

## 시나리오 개요

- 평시에는 낮은 부하를 유지하다가 특정 구간에서 급격히 RPS를 올린다.
- 이벤트 발행 직후, 예약 오픈, 배치 완료 직후 트래픽 유입을 가정한다.

## 고정 조건

- request/response는 작게 유지
- 커넥션은 재사용
- 서버 인스턴스 수와 자원은 고정
- 오토스케일은 비활성화하거나 별도로 통제

## 주요 변수

| 항목 | 값 |
| --- | --- |
| 평시 부하 | `100`, `300 RPS` |
| burst 부하 | `1000`, `3000`, `10000 RPS` |
| burst 지속 시간 | `10초`, `30초`, `60초` |
| burst 간격 | `1분`, `5분` |

## 실행 절차

1. 평시 트래픽을 2분 이상 안정적으로 유지한다.
2. 설정한 burst 부하를 즉시 인가한다.
3. burst 종료 후 다시 평시 부하로 복귀한다.
4. 이를 여러 차례 반복하며 tail latency와 회복 시간을 측정한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- peak 구간 에러율
- 큐 길이 또는 요청 적체량
- CPU 사용률
- 부하 해제 후 정상 회복 시간

## 기대 관찰 포인트

- burst 구간에서 `p99` 급등 폭과 복구 시간이 프로토콜별로 다를 수 있다.
- 커넥션과 스트림 재사용 전략 차이가 순간 부하 처리 능력에 영향을 줄 수 있다.

## 주의사항

- 오토스케일이 켜져 있으면 프로토콜 차이보다 scale-out 타이밍이 더 큰 영향을 줄 수 있다.
- load generator가 burst를 정확히 만들 수 있는지 먼저 검증해야 한다.
