# 02. Header-Heavy Request

## 목적

헤더와 메타데이터가 많은 요청에서 `REST API`와 `gRPC`의 전송 오버헤드를 비교한다.

## 시나리오 개요

- 본문은 작게 유지하고 헤더만 증가시킨다.
- 인증, 추적, 멀티테넌시, feature flag 상황을 가정한다.

## 고정 조건

- request/response body는 `1KB` 이하 유지
- 서버 비즈니스 로직은 단순 응답으로 고정
- 압축은 비활성화
- 클라이언트는 커넥션을 재사용

## 주요 변수

| 항목 | 값 |
| --- | --- |
| 헤더 개수 | `5`, `20`, `50`, `100` |
| 헤더 총 크기 | `512B`, `2KB`, `8KB`, `16KB` |
| client 수 | `5`, `50` |
| 목표 부하 | `200`, `1000`, `3000 RPS` |

## 헤더 구성 예시

- `Authorization` JWT: `1KB` 내외
- `x-request-id`
- `x-user-id`
- `x-tenant-id`
- `x-feature-flags`
- `b3` 또는 `traceparent` 계열 tracing header
- 실험용 추가 custom header 다수

## 실행 절차

1. 기본 헤더 세트와 확장 헤더 세트를 분리한다.
2. body 크기는 고정하고 헤더만 단계적으로 키운다.
3. 각 크기별로 `REST`와 `gRPC metadata`를 동일 의미로 구성한다.
4. 2분 warm-up 후 5분 측정한다.
5. 각 조건을 3회 반복한다.

## 수집 지표

- 평균 latency, `p95`, `p99`
- 네트워크 송수신 바이트
- 헤더 파싱에 따른 CPU 사용률
- 에러율

## 기대 관찰 포인트

- REST는 텍스트 헤더 처리와 큰 헤더 직렬화 부담이 더 커질 수 있다.
- `gRPC`는 metadata와 `HTTP/2` 헤더 압축 영향으로 차이가 완화될 수 있다.
- 다만 헤더가 매 요청마다 크게 달라지면 압축 이점이 줄어드는지도 함께 본다.

## 주의사항

- 프록시나 LB의 최대 헤더 크기 제한에 걸리지 않도록 별도 확인이 필요하다.
- 운영 환경에서 실제 사용하는 헤더 패턴을 최대한 반영하는 편이 좋다.
