Gradle에서 dependencies 블록 안에 선언하는 implementation, compileOnly, runtimeOnly 등은 이 라이브러리가 빌드 과정 중 어느 시점에 필요한지(Scope) 를 지정하는 키워드입니다.
이를 적절하게 구분해서 쓰면 빌드 속도가 빨라지고, 최종 배포 파일(Jar, Apk 등)의 용량을 줄일 수 있습니다.
주요 설정들의 의미는 다음과 같습니다.
1. implementation (가장 기본)
•
의미: 컴파일할 때도 필요하고, 실행(Runtime)할 때도 필요하다는 의미입니다.
•
특징: 우리가 작성하는 소스코드 안에서 직접 import 해서 사용하는 대부분의 라이브러리는 이것을 사용합니다.
•
예시: io.grpc:grpc-protobuf (직접 메시지 객체를 생성하고 다뤄야 하므로)
2. compileOnly
•
의미: 컴파일(빌드)할 때만 필요하고, 프로그램이 실제로 실행될 때는 필요 없다는 의미입니다.
•
특징: 최종 배포 파일(Jar 등)에 이 라이브러리가 포함되지 않아 용량을 줄일 수 있습니다.
•
예시:
◦
Lombok (@Getter, @Setter): 컴파일할 때 코드를 생성해주고 나면, 실행할 때는 롬복 라이브러리 자체가 필요 없습니다.
◦
방금 얘기한 javax.annotation-api: gRPC가 생성한 코드에 붙은 @Generated라는 어노테이션 때문에 컴파일러가 "이 클래스가 뭐지?"하고 에러를 뱉는 것을 막기 위해 추가합니다. 하지만 자바 가상 머신(JVM)은 프로그램을 실행할 때 이 어노테이션이 없어도 알아서 무시하므로 실행 시점에는 필요가 없습니다.
3. runtimeOnly
•
의미: 컴파일할 때는 필요 없지만, 프로그램이 실제로 실행될 때(Runtime)는 반드시 필요하다는 의미입니다.
•
특징: 소스코드 파일에서 import 해서 직접 쓰지는 않지만, 내부적으로 인터페이스의 실제 구현체를 갈아끼울 때 사용합니다.
•
예시:
◦
데이터베이스 드라이버 (MySQL, Oracle 등): 코드는 Java 표준 인터페이스(JDBC)로 작성(컴파일)하지만, 실제 실행할 때는 접속할 DB에 맞는 드라이버가 필요합니다.
◦
작성하신 io.grpc:grpc-netty-shaded: 작성하시는 코드에서는 gRPC 표준 인터페이스만 다루지만, 실제로 서버가 띄워져서 네트워크 통신을 하려면 내부적으로 'Netty'라는 엔진이 실행되어야 하기 때문에 사용합니다.
4. 기타 테스트용
작성하신 build.gradle에 있는 testRuntimeOnly 처럼 앞에 test가 붙은 것들은 테스트 코드를 돌릴 때만 적용하겠다는 의미입니다.
•
testImplementation: 테스트 코드를 컴파일하고 실행할 때 모두 필요 (예: JUnit, AssertJ)
•
testRuntimeOnly: 테스트 코드를 실행할 때만 필요 (예: junit-platform-launcher)
요약하자면:
•
내가 직접 import 해서 쓴다 👉 implementation
•
코드 생성/컴파일 에러 방지용이다 (실행 땐 안 씀) 👉 compileOnly
•
내 코드에선 안 쓰지만, 프로그램이 돌아가려면 뒤에서 필요하다 👉 runtimeOnly


Q) 어떻게 구별할 수 있음?

특정 라이브러리를 프로젝트에 추가할 때, 어떤 Scope(implementation, compileOnly, runtimeOnly 등)를 사용해야 하는지 확인하는 방법은 여러 가지가 있습니다.
크게 문서/저장소 확인 방법과 프로젝트 내에서 확인(검증) 하는 방법으로 나눌 수 있습니다.
1. 공식 문서 또는 Github README 확인 (가장 확실함)
가장 정확하고 일반적인 방법입니다. 라이브러리를 만든 개발자(혹은 팀)가 자신들의 라이브러리를 어떻게 추가해야 하는지 명시해 둡니다.
•
예시 (gRPC-Java 공식 Github): gRPC-Java의 공식 문서나 README를 보면 다음과 같이 명확하게 가이드가 적혀 있습니다.
Kotlin
implementation 'io.grpc:grpc-protobuf:1.64.0'
implementation 'io.grpc:grpc-stub:1.64.0'
compileOnly 'org.apache.tomcat:annotations-api:6.0.53' // necessary for Java 9+
runtimeOnly 'io.grpc:grpc-netty-shaded:1.64.0'
2. Maven Central 저장소 확인
mvnrepository.com 과 같은 저장소에서 라이브러리를 검색하면, 해당 라이브러리를 빌드 도구에 추가하는 스니펫을 제공합니다.
•
기본적으로 Maven Central은 implementation (Maven의 경우 compile) 탭을 기본으로 보여줍니다.
•
다만, Maven Central 스니펫은 저장소에서 기계적으로 제공하는 기본 포맷이므로 무조건 implementation으로 나오는 경향이 있습니다. 따라서 특별한 목적(예: DB 드라이버, 어노테이션 프로세서 등)을 가진 라이브러리라면 공식 문서를 교차 검증하는 것이 좋습니다.
3. 기능의 역할에 따른 논리적 추론 (경험적 방법)
어떤 역할을 하는 라이브러리인지 알면 Scope를 쉽게 유추할 수 있습니다.
•
내 소스 코드에서 import 문을 작성해서 클래스나 메서드를 직접 호출하는가?
◦
👉 implementation (대부분 90% 이상이 여기에 해당)
◦
예: Spring Boot, Gson, Retrofit, Protobuf 등
•
실제 코딩할 때는 쓰지 않지만, 실행(Runtime) 환경을 제공하거나 엔진 역할을 하는가?
◦
👉 runtimeOnly
◦
예: JDBC DB 드라이버 (mysql-connector-java), SLF4J 로깅 구현체 (logback-classic), 서버 엔진 (netty)
•
코드 작성이나 컴파일을 도와주는 용도이고, 컴파일이 끝나면 결과물에는 없어도 되는가?
◦
👉 compileOnly 또는 annotationProcessor
◦
예: Lombok, Java EE 어노테이션 (javax.annotation-api), MapStruct
4. Gradle 명령어로 현재 적용된 트리 확인
이미 프로젝트에 추가해 둔 라이브러리들이 어떤 Scope로 어떻게 엮여 있는지(Transitive Dependency 포함) 확인하고 싶다면 터미널에서 아래 명령어를 사용할 수 있습니다.
Shell Script
# 전체 의존성 트리 확인
./gradlew dependencies

# 특정 설정(예: compileClasspath)의 의존성만 확인
./gradlew dependencies --configuration compileClasspath
이 명령어를 치면 트리 형태로 runtimeClasspath, compileClasspath 등 어느 단계에 해당 라이브러리가 포함되어 있는지 상세하게 보여줍니다.
5. IDE(Android Studio / IntelliJ)의 기능 활용
Android Studio 우측의 [Gradle] 패널을 열어보면:
•
[프로젝트명] -> Tasks -> help -> dependencies 를 더블클릭하여 위 명령어를 쉽게 실행할 수 있습니다.
•
최신 버전의 IDE에서는 Dependencies 분석 도구(Dependency Analyzer) 를 제공하여 UI 형태로 각 라이브러리가 어느 Scope에 속해 있고 용량을 얼마나 차지하는지 시각적으로 보여줍니다. (View -> Tool Windows -> Dependencies)
